## Блок 1: Наследование (10 мин)

### Проблема: два почти одинаковых класса

```python
class Manager:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary


class Developer:
    def __init__(self, name, salary):  # точно такой же конструктор
        self.name = name
        self.salary = salary
```

Код повторяется, и при каждом изменении править нужно оба класса. Знакомая ситуация:
на семинаре 4 повторяющийся код мы выносили в функцию — здесь общее выносят
в **базовый класс**.

### Базовый и дочерний классы

```python
class Employee:
    """Сотрудник компании — базовый класс."""

    def __init__(self, name, salary):
        self.name = name
        self.salary = salary

    def work(self):
        return f"{self.name} работает"


class Manager(Employee):  # Manager — наследник Employee
    """Менеджер."""


manager = Manager("Анна", 150_000)
print(manager.work())  # метод достался от базового класса
```

Наследник получает **все** атрибуты и методы базового класса. Базовый класс называют
родительским, класс-наследник — дочерним.

### Расширение и super()

Чаще наследнику нужны свои данные. Он описывает собственный `__init__`, а работу
базового класса переиспользует через `super()`:

```python
class Developer(Employee):
    def __init__(self, name, salary, language):
        super().__init__(name, salary)  # базовый класс заполнит name и salary
        self.language = language  # собственный атрибут наследника
```

### Переопределение методов

Наследник может заменить метод базового класса своей версией — или **дополнить** его,
вызвав `super()`:

```python
class Designer(Employee):
    def work(self):  # заменяем полностью
        return f"{self.name} рисует макеты"


class TeamLead(Employee):
    def work(self):  # дополняем
        return super().work() + " и проводит встречи"
```

Python ищет метод сначала в классе самого объекта и только потом в базовом классе.

### isinstance()

Объект наследника — представитель сразу двух классов: своего и базового.

```python
developer = Developer("Иван", 180_000, "Python")

isinstance(developer, Developer)  # True
isinstance(developer, Employee)  # True — наследник «является» сотрудником
isinstance(Employee("Ольга", 120_000), Developer)  # False — обратное неверно
```

> **Атрибут класса.** Если переменную задать прямо в теле класса (`company = "МФТИ"`),
> она будет общей для всех экземпляров — в отличие от атрибутов, которые создаёт
> `__init__` для каждого объекта отдельно.

> **Подробнее:** см. файл [`examples/01_inheritance.py`](examples/01_inheritance.py)

## Блок 2: Полиморфизм и утиная типизация (10 мин)

### Один вызов — разное поведение

**Полиморфизм** («много форм») — возможность вызвать один и тот же метод у объектов
разных классов и получить поведение, подходящее каждому:

```python
staff = [
    Employee("Ольга", 120_000),
    Manager("Анна", 150_000, deals=4),
    Contractor("Иван", rate=2_000, hours=90),
]

for person in staff:
    print(person.name, person.monthly_pay())  # у каждого класса своя версия метода
```

Вызывающему коду не нужно знать, кто перед ним. Без полиморфизма пришлось бы писать
цепочку проверок:

```python
if isinstance(person, Manager):
    pay = person.salary + person.deals * 5_000
elif isinstance(person, Contractor):
    ...
```

Такой код приходится править при появлении каждого нового класса сотрудника,
а цикл выше — не приходится.

### Утиная типизация

> «Если нечто выглядит как утка, плавает как утка и крякает как утка,
> то это, вероятно, и есть утка».

Python не проверяет, от какого класса произошёл объект, — ему важно, **есть ли
у объекта нужный метод**. Поэтому полиморфизм работает и без общего базового класса:

```python
class CleaningRobot:
    name = "Робот-пылесос"

    def monthly_pay(self):
        return 3_000


def print_payroll(workers):
    for worker in workers:
        print(worker.name, worker.monthly_pay())


print_payroll([Manager("Анна", 150_000, 4), CleaningRobot()])  # работает
```

Робот не наследует `Employee`, но умеет всё, что нужно функции. Интерфейс важнее
родословной.

Обратная сторона: если нужного метода нет, ошибка обнаружится только при вызове —
`AttributeError`. Статические способы описать ожидаемый интерфейс (абстрактные классы
и `Protocol`) разберём на семинаре 7.

> **Подробнее:** см. файл [`examples/02_polymorphism.py`](examples/02_polymorphism.py)

## Блок 3: Композиция классов (10 мин)

### «Является» против «имеет»

Связать два класса можно двумя способами, и выбор между ними — это выбор между двумя
вопросами:

| Вопрос | Связь | Пример |
|--------|-------|--------|
| Объект **является** частным случаем другого? | наследование | менеджер **является** сотрудником |
| У объекта **есть** другой объект? | композиция | у сотрудника **есть** график работы |

При композиции объект просто хранится в атрибуте другого объекта:

```python
class Schedule:
    def __init__(self, hours_per_week, remote):
        self.hours_per_week = hours_per_week
        self.remote = remote


class Employee:
    def __init__(self, name, schedule):
        self.name = name
        self.schedule = schedule  # не наследуем график, а храним его

    def describe(self):
        return f"{self.name}: {self.schedule.hours_per_week} ч/неделю"
```

График можно заменить другим или переиспользовать для нескольких сотрудников —
объекту это безразлично.

### Класс, который состоит из других объектов

```python
class Department:
    def __init__(self, title):
        self.title = title
        self.employees = []

    def hire(self, employee):
        self.employees.append(employee)

    def headcount(self):
        return len(self.employees)
```

Отдел не «является» сотрудником — он из них состоит.

### Почему композиция обычно лучше

Соблазнительно сделать «отдел — это список сотрудников» и унаследоваться от `list`.
Но тогда отдел получит **весь** интерфейс списка: его можно будет отсортировать,
перевернуть, сложить с другим списком — действия, которые для отдела бессмысленны.

Композиция даёт ровно те действия, которые нужны (`hire()`, `headcount()`), создаёт
меньше зависимостей между классами и не ломает инкапсуляцию: наследник опирается
на устройство базового класса, а составной объект — только на его интерфейс.

> **Рекомендация из лекции:** по возможности предпочитайте композицию наследованию.
> Наследование уместно, когда объект действительно является частным случаем другого
> и может подменить его в любом месте программы.

> **Подробнее:** см. файл [`examples/03_composition.py`](examples/03_composition.py)

### Множественное наследование и проблема «ромба»

Класс можно построить сразу на нескольких базовых:

```python
class Bookkeeper(SalaryEmployee, FinanciallyResponsiblePerson):
    """Бухгалтер — и сотрудник с зарплатой, и материально ответственное лицо."""
```

Если у обоих родителей есть метод с одинаковым именем, вызовется версия первого
из них: порядок поиска задаётся **MRO** (`Bookkeeper.__mro__`). Поменяв родителей
местами, можно изменить поведение класса, не тронув в нём ни строки, — поэтому
множественного наследования стараются избегать.

### Проблемы наследования

| Проблема | В чём суть |
|----------|------------|
| Хрупкий базовый класс | наследники зависят от устройства базового класса, и его изменение ломает их |
| «Йо-йо» | чтобы понять один метод, приходится прыгать по длинной цепочке наследников |
| «Круг-эллипс» | математическая иерархия не совпадает с программной: квадрат как наследник прямоугольника ломает код, рассчитанный на прямоугольники |
| «Взрыв классов» | иерархия становится сложнее задачи, которую решает |

Отсюда **принцип подстановки Лисков (LSP)**: код, работающий с базовым классом, должен
работать и с любым его наследником, ничего о нём не зная.

### Аннотации типов и import

```python
import math
from math import sqrt, pi


def repeat(text: str, times: int) -> str:
    return text * times


salaries: list[int] = [120_000, 150_000]
```

Аннотации не влияют на работу программы: это подсказки человеку и инструментам
проверки. В нашем проекте типы проверяет `uv run ty check`.

### Декораторы и @property

**Декоратор** — функция, которая оборачивает другую функцию, добавляя поведение вокруг
её вызова. Запись `@decorator` над функцией равносильна `function = decorator(function)`.

`@property` превращает метод в вычисляемый атрибут — к нему обращаются без скобок:

```python
class Employee:
    @property
    def yearly_salary(self):
        return self.monthly_salary * 12


employee.yearly_salary  # считается при каждом обращении
```
